# Secret rotation

Rotate a secret on a schedule, when someone with access leaves, or immediately when it may have
leaked (pasted in a log, committed, sent in chat). For a suspected leak, rotate first and investigate
after.

Never write a secret value into Git, a GitHub issue or PR, a Docker build argument, or this vault.

## Inventory

| Secret                             | Where it lives                                                                  | Effect of rotating                     |
| ---------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------- |
| `BETTER_AUTH_SECRET`               | Dokploy app environment (staging), `.env` (self-hosted)                         | Signs every user out                   |
| PostgreSQL password                | PostgreSQL role + `DATABASE_URL` (staging) or `POSTGRES_PASSWORD` (self-hosted) | App restart                            |
| `MAIL_SMTP_URL` credentials        | Mail provider + app environment                                                 | App restart; none on staging (Mailpit) |
| `STAGING_DEPLOY_SSH_KEY`           | GitHub `staging` environment + `/root/.ssh/authorized_keys` on the VPS          | None if done in order                  |
| `PREVIEW_DEPLOY_SSH_KEY`           | GitHub `previews` environment + `/root/.ssh/authorized_keys` on the VPS         | None if done in order                  |
| Dokploy deploy tokens              | `/root/.config/shadergrove-*-deploy-token` on the VPS                           | None if done in order                  |
| `ADMIN_USER` administrator SSH key       | Operator machine + `/home/ADMIN_USER/.ssh/authorized_keys`                            | None if done in order                  |
| `GITHUB_RELEASES_TOKEN` (optional) | Website server environment                                                      | None                                   |

Per-preview database and account passwords are generated by the preview controller and deleted with
the preview; remove and re-add the `preview` label to regenerate them.

## Application secrets

### `BETTER_AUTH_SECRET`

1. Generate a value: `openssl rand -base64 32`.
2. Staging: replace it in the Dokploy application's environment and redeploy. Self-hosted: replace it
   in `.env`, then `docker compose up -d shader-studio`.
3. Every session is invalidated; users sign in again. Accounts and shaders are untouched.

### PostgreSQL password

The `postgres` image reads `POSTGRES_PASSWORD` only when it first creates the data volume. Changing
the variable alone does nothing; change the role's password in the database, then the app's
configuration.

1. Generate a value without URL-special characters, since it goes into `DATABASE_URL`:
   `openssl rand -base64 32 | tr -d '/+='`.
2. Set it on the role with `psql`'s `\password`, which prompts for the value so it never appears in
   shell history or the process list. Self-hosted:

   ```sh
   docker compose exec postgres psql -U shader_studio -d shader_studio -c '\password shader_studio'
   ```

   Staging: run the same command with `sudo docker exec -it` in the database container, using the
   user and database from `DATABASE_URL`.

3. Update `POSTGRES_PASSWORD` in `.env` (self-hosted) or the password inside `DATABASE_URL` in Dokploy
   (staging), then restart the app.

### SMTP credentials

Create the new credential at the mail provider, update `MAIL_SMTP_URL`, restart the app, send a
password reset to a test account, then revoke the old credential at the provider.

## Deployment credentials

Add the new credential, prove it works, then remove the old one — never the reverse, or CI is locked
out.

### `STAGING_DEPLOY_SSH_KEY`

1. Generate a key pair without a passphrase: `ssh-keygen -t ed25519 -N '' -C staging-deploy -f staging-deploy`.
2. On the VPS, append the public key to `/root/.ssh/authorized_keys` with the same restrictions as the
   existing line:

   ```
   command="/usr/local/sbin/deploy-shadergrove-staging",restrict ssh-ed25519 AAAA… staging-deploy
   ```

3. Replace the GitHub secret: `gh secret set STAGING_DEPLOY_SSH_KEY --env staging < staging-deploy`.
4. Push to `develop` (or re-run the latest `deploy-staging` job) and confirm it queues the deployment.
5. Delete the old key's line from `authorized_keys`, then delete both local key files.

### `PREVIEW_DEPLOY_SSH_KEY`

Same order with the preview controller's restriction:
`command="/usr/local/sbin/shadergrove-preview",restrict`. Replace the secret with
`gh secret set PREVIEW_DEPLOY_SSH_KEY --env previews < preview-deploy`, then confirm with
`gh workflow run pr-previews.yml --ref master -f pr=N` on a labelled PR before removing the old line.

### Dokploy deploy tokens

Each application's token is the last segment of its Dokploy deploy webhook URL. Regenerate the
webhook token in that application's settings in Dokploy, write the new token alone to
`/root/.config/shadergrove-staging-deploy-token` or `/root/.config/shadergrove-website-deploy-token`
(`sudo install -m 600 /dev/null FILE`, then edit), and confirm the next CI deployment is queued. The
Dokploy menu labels in this step have not been checked yet.

### `ADMIN_USER` administrator key

Keep your current session open throughout. Generate a new key, append its public key to
`/home/ADMIN_USER/.ssh/authorized_keys`, and from a second terminal confirm both a login and `sudo -n id`
with the new key. Only then remove the old line and replace `~/.ssh/vps-lab-01` locally. If you lock
yourself out, recover through the provider console as described in [VPS security](../vps-security.md).

## Verify

- `GET /api/health` returns HTTP 200 with `{"status":"ok"}` after any app restart.
- The next CI deployment of studio and website reaches Dokploy.
- The old credential no longer works (old SSH key refused, old SMTP credential revoked).

Record which secrets were rotated and when — not their values — then set `last_verified`.

## Roll back

Until the old credential is removed, switching back is just restoring the previous value. After it
is removed, there is no rollback: generate another new credential and repeat.
